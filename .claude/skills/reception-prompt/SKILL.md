# 受付の指示文を直す

指示文は `web/server/prompt.mjs`。Claude には、1 行に 1 つの JSON(最初の `say` に `intent`・`stage`・`handoff` を足す)で返させ、画面は 1 行ごとに読み上げ・表情・視線・指さしを動かす。

## 試す手順(鍵は環境変数。値は表示しない)

1. 動かす: `cd web && npm run build && ANTHROPIC_API_KEY=… node server/index.mjs`(司令塔から渡された鍵の環境変数を `ANTHROPIC_API_KEY` として渡す)。
2. 3 つの代表の質問を、本物の Haiku で流す(`curl -N -X POST localhost:8787/api/chat …`、`place.landmarks` に `お手洗い`・`入口` を入れる):
   - 目印が話に出る「お手洗いはどこですか」→ `stage: guide`、聞き返さず案内する。`gaze` は `landmark:お手洗い`、`motion` は `point`
   - 用件が不明な「あの、すみません」→ `stage: need`、1 つだけ聞く
   - 場所の情報に無い「ここの営業時間は?」→ `stage: handoff`、`handoff: true`、人へつなぐ
3. 形が崩れたら `server/brain.mjs` の `parseLine` が拾えているか、`node --test` で確かめる。崩れ方は `test/brain.test.mjs` に足す。
4. 返事の時間は `conversation-latency` のスキルで測る。

## 分かったこと(2026-11-02)
- **`stage` の決め方**: お客さんが話しかけてきて、用件がまだ分からない(「あの、すみません」)ときは **need**(聞き返す)。**greet は、お客さんが黙って近づいてきたときの、こちらからの声かけだけ**。(Haiku で直す試験の 1 回目に、need を greet にして落ちた。)
- **距離の数字は、渡す側で言葉にする**。指示に「読み上げない」と書くだけでは、短い質問で数字が混ざる回が残る。`describeLandmarks`(目印を文にする所)で「約 3.8m」を「奥のほう」「数歩先」に直してから渡すと確実。

- 指示に「用件が分からないうちは、案内を始めず聞く」とだけ書くと、**目印の名前が出ていても聞き返す**(「お手洗いはどこですか」に「どちらをお探しでしょうか」)。「目印の名前や、はっきりした用件が入っているときは、聞き返さずすぐ案内する」と書き、**3 つの例(案内・聞き返し・人へつなぐ)を JSON の形のまま入れる**と直った。形の説明より、例のほうが効く。
- 「見えた様子」を Claude に書かせると、画面側で作って渡した言葉の言い直しになり、トークンと時間を使う。画面側の言葉をそのまま出す。
- 方向の言葉(右・左・手前・奥)は、キャラと向かい合ったお客さんから見た向きで渡す(場所の柱の `left_deg` はキャラの左が正なので、符号が逆)。指示文にも「お客さんから見て」と書く。
- 出力の形を変えて最初の文字までの時間を縮める試みは、API のばらつきに埋もれて、はっきりした差が出なかった。形は、画面の作りやすさ(用件が先に見える)で選ぶ。
- **履歴は、指示した出力の形(1 行 1 つの JSON)のまま渡す。** 前の返事を「ふつうの文」で履歴に入れたら、モデルがそれをまねて、短い質問(「入口は」)にだけ、JSON でなく文章で答える回が出て、画面が無言になった。履歴の返事を JSON の行に戻して直った(`assistantLines`)。それでも文章で返ってきた回は、その文を読み上げる(`brain.mjs` の救済。サーバーの画面に生の出力が残る)。**形が崩れたら、まず履歴の形を疑う。**
- あいづちの声(「はい。」「ええ。」「なるほど。」「そうですね。」「はい、はい。」)は、本当の返事より前に鳴るので、**1 秒以内の長さ**にする。「はい、承知しました。」(約 1.6 秒)は、本当の返事を後ろへ押すので外した。
- **距離の数字は、そのまま読み上げさせない。** 目印に「左奥、約 1.6m」と渡すと、モデルが「約 1.6m の方にございますよ」と読み上げる。指示に「距離の数字は、すぐそば・少し先・奥のほう、のような言葉にする。方向は、はっきり言う」と書いて直した。
- **動きの一覧は、そのキャラが使える物だけを渡す。** 人型は手続きの動き(うなずき・指さし ほか)、人型でないキャラ(rig)は動きのファイルがある物だけ。指示文の「motion は次から選ぶ」と、返事の検証(一覧に無い名前は none)の両方を、キャラごとの一覧にする。指さしの動きが無いキャラでも、視線(目印を見る)で案内は伝わる。

## 段を下げても合格するか(2026-11-02 の固定の試験)

固定の試験: `web/scripts/prompt-eval.mjs`(本物の Haiku を 12 回呼び、返事を機械で判定。合格は 12 回中 11 回以上)。**出来の悪い最初の版の指示文**(`web/test/fixtures/prompt_v0_degraded.mjs`、この試験で 5/12 の不合格)を、まっさらな文脈のモデルが、このスキルだけを読んで直す。モデルごとに専用の箱(試験・最初の版・このスキルの写し・課題文だけのフォルダ)を作り、箱の外は触らせない。試験は最大 6 回。報告は信じず、**私が箱の `prompt.mjs` を独立に 2 回流して**確かめた。

| 段 | モデル / effort | 合否(独立に 2 回) | 試験を流した回数 | 時間 | トークン(合計) |
|---|---|---|---|---|---|
| 1 | Opus 5.5 / xhigh | 12/12・12/12 | 2 | 121.0 秒 | 143,741 |
| 2 | Opus 5.5 / high | 12/12・12/12 | 2 | 88.7 秒 | 138,135 |
| 3 | Opus 5.5 / medium | 12/12・12/12 | 1 | 61.9 秒 | 134,685 |
| 4 | Sonnet 5.5 / high | 12/12・12/12 | 1 | 39.8 秒 | 133,181 |
| 5 | Sonnet 5.5 / medium | 12/12・12/12 | 1 | 45.5 秒 | 133,531 |
| 6 | Haiku 5.5 | 12/12・12/12 | 3(1 回目は 7/12) | 126.9 秒 | 144,368 |

- 費用: 単価の表が手元に無いので、ドルは書かない(トークン数は、読み込んだ文脈を含む合計)。同じトークン数なら、単価は Haiku < Sonnet < Opus。**1 回で合格したのは Opus medium・Sonnet high・Sonnet medium。時間が最も短いのは Sonnet high(39.8 秒)**。Haiku は単価が最も安いが、3 回かかり、トークンは最多・時間は Opus xhigh と同程度。
- 読み取り: **この固定の試験では、最も安い Haiku まで合格した**。ただし、Haiku は 1 回目に落ちた(7/12。距離の数字の読み上げ 3 件、用件が不明な話しかけを `greet` にした 2 件)。それより上の段は、すべて 1〜2 回で通った。n は各段 1 回なので、段の差は目安(順位をつける材料にはならない)。試験は、スキルに答えが書いてある課題なので、やさしめ。
- 全段が同じ直し方をした: 目印が出たら聞き返さず案内する・JSON の形の例を入れる・出力の形を履歴と同じにする・距離の数字を言葉にする。
- **Haiku が落ちて分かった、足りなかった知識**(上に書き足した):
  - `stage` の決め方: お客さんが話しかけて用件が不明なら **need**。**greet は、近づいてきた(きっかけ)ときだけ**。
  - 距離の数字は、指示に「読み上げない」と書くだけでは 3 件落ちた。**渡す側(`describeLandmarks`)で、数字を「すぐそば・数歩先・奥のほう」の言葉に直してから渡すのが確実**で、Opus と Sonnet の全段が、最初からそうしていた。Haiku も、これを足して合格した。
- 使い分けの目安: この種の仕事(指示文の直し、試験が決まっている)は、**Sonnet medium を既定**にし、落ちたら Sonnet high → Opus へ上げる。Haiku は、試験が決まっていて、直しを何回か回せるときに使える。

## キャラの性格の指示文を足す(2026-11-03、見本のキャラ)
- 置き場: `characters/<id>/persona.md`(`character.json` の `persona`)。システム指示の「話し方」「受付の流れ」「出力の形」はそのまま、性格はその上に足す。
- 試験: `web/scripts/persona-eval.mjs --character <id> --port <ポート> --rounds 2`(本物の Haiku、読み上げなし)。場面は 8 つ(用件不明・自己紹介・目印の案内・仕組みを聞かれる・出演者と料金を聞かれる・ステージの前と後)。形と場面ごとの決まりを正規表現で判定。1 版目で 16/16。
- **時制を決めつけない**: 最初の版に「もうすぐ初ステージに立つ」と書いたら、「どうだった?」(過去)の質問に合わなかった。経験が「これから」か「もう」かは、【見えている様子】(`scene`)に合わせると書く。
- 「…」や記号は読み上げに向かない。persona に「記号は使わない」と書くと、単独の質問ではほぼ出なくなった(場面つきの質問で「…」が混ざった回があったのは、書く前の試しだけ)。
- 仕組みを聞かれる質問には「お話しするのが得意なんです」くらいにとどめる、と書くと、Claude・AI・モデル・API を出す回は 0/2 だった。

## カスタムの表情を足す(2026-11-03、見本のキャラ)
- `character.json` の `expressions` に名前を足し、`expression_hints`(名前 → いつ使うか、60 字まで)に日本語で書く。無い VRM は近い標準の表情に自動で落ちる(`expression_fallback` で落とし先を決められる)。
- 説明は「その気持ちがはっきり出る場面」を書く(例「照れ。ほめられたとき、かわいいと言われたとき」)。指示文は「気持ちがはっきり出る場面だけ。ふだんは neutral か happy」と添える。これで、落ち着いた場面(用件不明・案内)にカスタムが出た回は 0/4、気持ちの場面では 12/16 で使われた。
- 試験: `web/scripts/expression-eval.mjs`(標準 vs カスタム、本物の Haiku)。場面ごとの「合う表情の集合」は、厳しくしすぎない(標準の版が不合格に見えるだけの差が出る)。時間は +24 ms で、ばらつきの中。
