# 線を 1 本ずつ合わせて、入れるたびに試験を通す

合わせ係は、作業の線を読むだけ・入れるだけ。中身は直さない(直すのはその線の持ち主)。

## 手順
1. 合わせる線が別の作業フォルダで開かれている時は、そこでは合わせない。合わせ係の線で合わせ、最後に合わせる線の作業フォルダで `git merge --ff-only <合わせ係の線>` で進める(その作業フォルダが空であることを先に見る)。
2. 合わせ係の線を、合わせる線の最新まで進める: `git merge --ff-only yurukyara-dev`。土台で試験を 1 回流し、数を控える(後の比べの元)。
3. 各流れの札の「入れてほしいコミット」と、`git log --oneline yurukyara-dev..<線>` が同じかを先に見る(札に無いコミットが混ざっていたら入れずに聞く)。
4. 線ごとに `git merge --no-ff --no-commit <線>` → 試験 → 通ったらコミット、落ちたら `git merge --abort`。
   - コミットの前に試験が流せるので「コミットの前に点検」の決まりを守れる。取り消しに revert の記録が残らない(後で同じ線を入れ直せる)。
   - 必須の門: `cd web && YC_BROWSER_TESTS=1 npm test`(= `node --test`。頭脳と声の鍵は子の環境から外す。**画面なしの Chrome の試験は `YC_BROWSER_TESTS=1` が無いと「飛ばし」になるだけで、落ちても気づけない**)、`python tools/prepush_check.py`、**git の pre-push と同じ形の `python -I tools/prepush_check.py`**、フックの試験。足すと良い物: `npx vite build`、作例の検査、フックの壊す試験、各流れの試験(python の unittest など)。
   - 1 本を差し戻した後に次の線へ進む前に、次の線が差し戻した線のコミットを含まないかを見る: `git merge-base --is-ancestor <差し戻した線の頭> <次の線>`(含んでいなければ、そのまま次を入れてよい)。
   - 試験の台本は 1 本にまとめ、`machine_lock.py run --kind cpu` で包む(終われば札が自動で返る)。試験の数・飛ばした数・かかった秒を毎回控える。
5. 線ごとに `git diff --name-only <土台>...<線>` を、その流れの「書いてよい場所」と比べる。外のファイルは「持ち主のいる場所」か「持ち主なし」かに分けて記録する。持ち主のいる場所を別の流れが書き換えていたら、入れずに返す。
6. 全部入れたら、話す試験を 1 回(空いた番号でサーバーを起こし、頭脳と声の鍵を環境から外し、自分で起こした PID だけを止める)。WebGL を使う試験は GPU で描き、描画役が CPU(SwiftShader)なら止める。GPU は `machine_lock.py run --kind gpu` で包む。
7. 合わせる線を origin へ送る(上書きの push はしない)。送る前に `gh repo view --json visibility` で非公開を確かめる。push の前に動く点検が、送る物と同じ木を見ているかを確かめる(合わせ係の作業フォルダから送れば、同じ中身の木を点検する)。送った後に `git ls-remote origin refs/heads/<線>` で頭が同じかを見る。

## フックを登録する前の確かめ(登録は人か、許しを得たセッションがする)
- フックの台本を、Claude Code と同じ形の入力(`{"tool_name", "tool_input", "cwd"}` の JSON を標準入力へ)で直接呼ぶ。環境変数 `CLAUDE_PROJECT_DIR` で「リポジトリ」を決める。
- 偽の鍵は実行のときに組み立て、使い捨ての木(scratchpad の中で `git init`)に入れて `git add` する。記録では伏せる。
- 止めた記録の行き先を `YC_HOOK_LOG` で scratchpad へ向ける(リポジトリの中に記録を残さない)。
- 確かめる組: 偽の鍵入りの commit → 2 / 鍵なしの commit → 0 / リポジトリの外へ Write・Edit(偽の鍵入り)→ 0 / 中へ Write(偽の鍵入り)→ 2 / 中へ Write(鍵なし)→ 0。

## 落とし穴(実測)
- **流れの直しで、push の前の点検が `python -I` の時だけ落ちた**(11/6 合わせ②)。S6 が `prepush_check.py` に同じフォルダの部品(`import termlist`)を足し、`-I`(isolated)では台本のフォルダが sys.path に入らないため `ModuleNotFoundError`。普通の `python tools/prepush_check.py` は通るので、門で気づけなかった。`git push --dry-run` でも pre-push は動いて止まる。`--no-verify` でくぐらず、持ち主に直してもらう(例: 台本の頭で自分のフォルダを sys.path に足す)。門に `-I` の形を足した。
- 語の一覧の読み方(`cs:`・`re:`・`rei:`)が新しくなると、同じ一覧でも当たるファイルが増える。流れが自分の線の古い読み方で「0 件」と言っても、合わせた木の読み方で数え直す。当たった所は語を写さず、ファイルと行の番号だけを返す。
- 画面なしの Chrome の試験が入ると、`npm test` が 7 秒から 48 秒になった。編集のたびに `node --test` を回すフック(60 秒で打ち切り)に近い。合わせのたびに秒を控え、近づいたら持ち主に知らせる。
- 2 つの流れが、持ち主の無い同じファイルを直していた。直した所が離れていれば自動で合わさる。合わせた後に `node --check <ファイル>` で構文を確かめる。
- 後の流れに頼る試験は、頼る流れが入るまで「飛ばし」になる。順番どおりに入れたら飛ばしが 0 になるかを見る(S4 の 2 件は S3 の後で 0 になった)。
- 作例のフォルダ全体のハッシュを見る検査は、別の流れがそのフォルダに新しいファイルを足すと NG になる。変わったと出たのが「新しく足したファイルだけ」かを見る。元のファイルが変わっていなければ欠陥ではない。基準の書き直しは検査の持ち主がする。
- 履歴の点検で「鍵らしい代入」が出たら、値を伏せて(頭 6 字と終わり 4 字だけ)中身を見る。試験用の仮の値(`TOKEN = "unit_test_…"` など)のことがある。
- `node_modules` を作業フォルダの間で共有している時は、作業フォルダで `npm ci` をしない(共有の中身が消える)。package.json と lock が変わっていなければ `npm test` で足りる。
- Git Bash で `git show <線>:.claude/…` のように `:` と `/` を含む引数を渡すと、道の書きかえで壊れる。`MSYS_NO_PATHCONV=1` を前に付ける。
- `git rev-parse --short` は 1 つしか受けない。複数の線の頭は 1 つずつ聞く。
- 試験の記録に、入れない語の一覧に当たった語を写さない(「」の中を伏せる)。
- 合わせ係のセッションからも、作業フォルダの `.claude/` の下はファイルを書く道具で書けない(設定の守り。「設定の場所と見分けられない」と返る)。迂回しない。スキルの下書きは板の控えに置き、置くのは人か、許しを得たセッションにする。置く物は「新しい・違う・同じ」と語の点検の結果を表にして渡す。
- 板の控えと木の版を比べる時は、改行の違い(CRLF と LF)だけで「違う」と出る。`diff --strip-trailing-cr` で数える。
- **流れの作業フォルダで通った試験が、合わせ係の木でだけ落ちることがある(改行の形)**(11/6 合わせ③、S3)。Windows は `core.autocrlf=true` なので、取り出し直した木では md が CRLF になる。流れが自分で書いたファイルは取り出し直していないので LF のまま(`git ls-files --eol <file>` で `i/lf w/lf` と `i/lf w/crlf` の違いが見える)。ファイルの中身を丸ごと `assert.equal` で比べる試験がここで落ちる。合わせ係の木は「新しく取り出した木」と同じなので、ここで落ちた物は本人や審査の人の写しでも落ちる。差し戻し、比べる前に改行をそろえる直し(または .gitattributes)を頼む。理由は、流れの木を読むだけの小さな台本で LF と CRLF を並べて確かめると早い。
- `YC_BROWSER_TESTS=1` のありなしで件数が変わる(合わせ③: あり 297 件・飛ばし 0 / なし 294 件・飛ばし 6)。画面の試験の中の小さな試験も数に入るため。比べる時は同じ形どうしで比べる。編集ごとのフックと同じ形(なし)の秒も 1 回測る(合わせ③で 6.8 秒)。
- 話す試験の口の大きさ `mouth_max` は、別の流れが声の無い時の「ピッ」の音を変えると下がる(合わせ③: S5 の音色の変更で ようこそくん 0.33 → 0.26。口を音の大きさから作っているため)。合格の中でも、合わせごとに数を控えて比べる。
- 試験の台本(門・話す試験)はリポジトリの外(scratchpad)に置き、`machine_lock.py run --machine <機械> --kind cpu --procs 4 ... -- python gate.py "<ラベル>"` で包む。記録は 1 回 1 行の JSON(試験ごとの rc・秒・数・最後の行)。公開前の語は `「…」` を伏せ、当たったファイルの名前だけを残す。

## 合わせ④で学んだ事(11/7 00:15〜00:40、実測)
- **`.gitattributes`(`* text=auto` と `eol=lf`)を、`core.autocrlf=true` で取り出し済みの木へ合わせても、`git status` は汚れない**(合わせ④の S6)。先に `git ls-files --eol | awk '{print $1}' | sort | uniq -c` で索引に `i/crlf` が 0 かを見る(1 本でもあると、`text=auto` で「変わった」と出る)。合わせた後は、後の合わせで書かれたファイルだけが LF になり、触っていないファイルは CRLF のまま。
- 合わせ係の木を LF に取り出し直すのは、木の中身のハッシュを基準と比べる検査(作例の検査 K0)の基準が直ってから。基準が CRLF の形で取られていると、取り出し直しただけで落ちる。
- 改行の差し戻しは、持ち主の「比べる前に改行をそろえる」直し(S3)と、`.gitattributes`(S6)の両方を入れた。S3 を先に入れて CRLF の木で通る事を見てから S6 を入れると、どちらか片方に頼らない事が確かめられる(346/346 → 346/346)。
- 線の木が合わせる線と同じ(`git diff --stat yurukyara-dev <線>` が空)なら、合わせない。空の合わせのコミットを作らない(S7)。
- まだ入れない線は、作業フォルダを触らずに `git merge-tree --write-tree --name-only HEAD <線>` でぶつかりを下見できる(終わりの番号 0 = ぶつかりなし)。
- **dev → main の早送りの前に、main に無くて dev にある物を見る**: `git ls-tree --name-only main <道>` と dev を比べる(合わせ④で `docs/plan/` が dev にだけあった)。公開の木から外すと決まった物なら、書き換えの「落とす道」の一覧に入っているかを確かめてから進める。main の作業フォルダが空か・書き込む量(`git cat-file -s` の合計、合わせ④は 約 2.8MB)・ディスクの空きも見る。
- Windows の git の pre-push の出力は cp932 で化ける。読む時は `python -I tools/prepush_check.py 2>&1 | iconv -f cp932 -t utf-8`(「push の点検: 問題なし」)。
- 話す試験の口は、S3 の口の戻しの直しが入って 0.688・0.689 に戻った(合わせ③は 0.327・0.260)。合わせごとの数を並べると、どの流れで変わったかが分かる。
- 板の控えには、丸ごと置く版(SKILL.md)と、スキルへ書き足す文(〜_norrie.md など)がある。比べの表で分けて渡す(書き足す文は人か司令塔が節を選んで入れる)。
- 「判定のファイルに `<<DONE>>` が出たら入れる」線は、ほかの線を先に入れて送ってから、時間を区切って待つ(合わせ④: 01:15 まで待つと決め、00:53 に出た)。出たら同じ門で入れ、開発の線と main をもう 1 回早送りして送る(送るのが 2 回になってよい)。待つ間に、記録・札・スキルを書いておくと、出た後は門と送るだけで済む。
- 主役のような新しいキャラが入ったら、話す試験にそのキャラを足す(`talk.py <id> mikan yokoso`)。形の検査(K1)は `characters/*/character.json` を全部回すので、新しいキャラも自動で入る。
- Git Bash の heredoc に、`r"…\…"` のような逆斜線を含む Python を書くと壊れる。台本は Write の道具でファイルに書いてから流す。

## 合わせ⑤で学んだ事(11/7 02:38〜02:59、実測)

## 合わせ⑥で学んだ事(11/7 04:56〜05:17、実測)
- **「対で入れる」コミットは、相手の流れのコミットがあるかを先に見る**。合わせ⑥: S3 の線の先 5555201(作例 4 体の人格の文)は、作例の検査 K0 の基準(S1 の持ち物)の直しと 2 本そろって初めて通る。`git log --oneline yurukyara-dev..w/s1-make3d` が空(S1 はまだ控えを当てていない)なので、S3 の札の決まりどおり、単独で通る e233935 までを id で入れた(`git merge --no-ff --no-commit e233935`)。線の頭ではなく id で入れれば、残りは次の合わせで入る。
- **見直し役(読むだけの流れ)はコミットが無い**。報告の行き止まり(blocker)・重大・高を、持ち主の流れの「各流れの次」へ写す。重大 0・高 0 の報告は、その事と中の数・持ち主だけを 1 行で写す。
- `machine_lock.py run --kind gpu` は、札と一緒に古い GPU の鍵(gpu_lock.py の形)も自動で書く(札の道具の「鏡」)。「札と GPU の鍵」は、この 1 つで両方になる(札の道具の作り ml_state.py の refresh_mirror を読んで確かめた。走っている間の鍵の中身は見ていない)。札が返った後、`gpu_lock.py status` は「空き」に戻っていた。

- **外した線が直って戻る時は、直しの線に土台(dev)の最新が入っていれば 1 回のマージコミットで済む**(`git merge --no-ff <直しの先>`。衝突 0)。手元の門 → 木の id(`git rev-parse HEAD^{tree}`)が門の木と同じことを見て → 確認台の写しを bundle で進め(段は 頭のすき間・大きさ・テレビ・VR と QR)→ 2D の頭のすき間は補いの台本(期待する先の id を渡す)→ 送る。全部で約 25 分。頭のすき間の組 `main` の 2D の 7 落ちは道具の限界(前から)で、合否は補いで見る。
- **確認台の写しの用意台本は、受け取りの参照に `+` を付ける**(早送りでない先へ替わらず、前の木のまま確かめが流れる)。流す前に「写しの先 = 期待の先」の行を見る。台本が無言で前の木を流す事故では、ssh を止めても確認台の側の python と node は走り続ける(孫まで残る)ので、命令の一覧(自分の台本の名前で絞る)で PID を見て、自分の物だけ `Stop-Process` する。
- 頭のすき間の組 `main` は 2D で「動き None」と落ちる(持ち主の道具が 2D の動きを流さない)。2D の合否は補いの `headgap11c_2d.py`(`gpu11c2.py headgap2d`)で見る。
- git の衝突を `<<<<<<<` の行ごと sed で消す時は、片側の中身が両方残ってよい物(スキルの学びの列)に限る。README のように場所が決まっている物は、印の間へ移す台本を書いて、印が 1 組・見出しが 1 つだけを数えて確かめる。
- Windows の Git Bash の `cat >> file <<'EOF'` に、日本語・バッククォート・アポストロフィが長く混ざると、全体が実行されず先頭の `cp` も走らない。長い文は Write で別のファイルにして `cat` で足す。
