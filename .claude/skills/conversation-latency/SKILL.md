# 返事の時間を測って縮める

目標は、ユーザーが話し終えてから、キャラの声が出るまで **1.2 秒以内**。言ってよいのは **測った数字だけ**(日付つき)。

## 何を測るか(画面の中)

`t0` = 声が最後に出ていた時刻(マイクの音量で判定)。文字で送ったときは送信した時刻。
`totalMs` = 最初の音が出た時刻 − `t0`。内訳は `/api/metrics` に残る:

| 項目 | 意味 |
|---|---|
| `t0ToSendMs` | 話し終わりから、聞き取りが確定してサーバーへ送るまで(聞き取りの遅れ) |
| `sendToFirstSayMs` | 送信から、最初の「読み上げる 1 文」が届くまで(Haiku) |
| `ttsFirstByteMs` | その 1 文の読み上げの、最初の音のかけらまで(ElevenLabs) |
| `valid` | 頭脳が Haiku で、声が ElevenLabs のときだけ true。仮の頭脳や字幕のみの値は、集計から外す |

## 手順

1. サーバーを起動: `cd web && npm run build && npm run server`(鍵は環境変数。`/api/status` で頭脳が haiku か確かめる)
2. 機械的に 10 回(頭脳と声だけ): `npm run measure -- 10` → 中央値・90 番目・1200ms 以内の回数が出る。`logs/latency_server.jsonl` に足される。
3. 画面で声を 10 回(聞き取りと再生を含む): ブラウザで開き、「声で話す」で 10 回話す。画面の下の「返事まで」と `GET /api/metrics`(`count`・`medianMs`・`p90Ms`・`underTargetRate`)を読む。iPhone でも同じ。
4. `docs/devlog_会話.md` に、日付・機械・回数・中央値・90 番目・目標内の割合を **そのまま** 書く。外れた回の原因も 1 行。

## 縮める順番(効いた順に試す。効かなかったものも devlog に残す)

1. **読み上げのモデル**: 2026-11-02 に短い文で測った最初の音まで(ElevenLabs、`pcm_24000`): `eleven_flash_v2_5` ≈ 290ms、`eleven_v4_turbo` ≈ 290〜520ms、`eleven_v4` ≈ 780ms。既定は flash(`ELEVEN_MODEL_ID` で替える)。
2. **最初の 1 文を短く**: 指示文で「1 文は 40 字以内」。最初の文が短いほど、読み上げが早く始まる。
3. **考えの行を短く**: 返事の 1 行目の `thought` が長いと、最初の `say` が遅れる。`seen` と `intent` は短く。
4. **先読み**: 文ごとに読み上げの取得を始め、前の文を話している間に次を用意している(`speaker.js` の `_pump`)。
5. **つなぎ**: 返事が来るまでの間は、うなずき(`NOD_AT_MS`)で間をつなぐ。数字は縮めない。縮めて見せるときは「一部を短くしています」と出す。
6. **聞き取りの遅れ**: ブラウザ内蔵の聞き取りは確定が遅いことがある。クラウドの聞き取りに替えたら、`t0ToSendMs` の差を測って書く。

## 守ること

- 目標を超えた回も隠さない。中央値と 90 番目の両方を書く。
- 仮の頭脳・字幕のみの回(`valid: false`)を、本物の数字として使わない。
- 読み上げの文字数は上限(`ELEVEN_DAILY_CHAR_CAP`)の枠を使う。測る回数は必要なだけにする。
