# 返事の時間を測って縮める

目標は、ユーザーが話し終えてから、キャラの声が出るまで **1.2 秒以内**。言ってよいのは **測った数字だけ**(日付つき)。

## 何を測るか(画面の中)

`t0` = 声が最後に出ていた時刻(マイクの音量で判定)。文字で送ったときは送信した時刻。
`totalMs` = 最初の音が出た時刻 − `t0`。内訳は `/api/metrics` に残る:

| 項目 | 意味 |
|---|---|
| `t0ToSendMs` | 話し終わりから、聞き取りが確定してサーバーへ送るまで(聞き取りの遅れ) |
| `sendToFirstSayMs` | 送信から、最初の「読み上げる 1 文」が届くまで(Haiku) |
| `ttsFirstByteMs` | その 1 文の読み上げの、最初の音のかけらまで(ElevenLabs) |
| `valid` | 頭脳が Haiku で、声が ElevenLabs のときだけ true。仮の頭脳や字幕のみの値は、集計から外す |

## 手順

1. サーバーを起動: `cd web && npm run build && npm run server`(鍵は環境変数。`/api/status` で頭脳が haiku か確かめる)
2. 機械的に 10 回(頭脳と声だけ): `npm run measure -- 10` → 中央値・90 番目・1200ms 以内の回数が出る。`logs/latency_server.jsonl` に足される。
3. 画面で声を 10 回(聞き取りと再生を含む): ブラウザで開き、「声で話す」で 10 回話す。画面の下の「返事まで」と `GET /api/metrics`(`count`・`medianMs`・`p90Ms`・`underTargetRate`)を読む。iPhone でも同じ。
4. `docs/devlog_会話.md` に、日付・機械・回数・中央値・90 番目・目標内の割合を **そのまま** 書く。外れた回の原因も 1 行。

## 縮める順番(効いた順に試す。効かなかったものも devlog に残す)

1. **読み上げのモデル**: 2026-11-02 に短い文で測った最初の音まで(ElevenLabs、`pcm_24000`): `eleven_flash_v2_5` ≈ 290ms、`eleven_v4_turbo` ≈ 290〜520ms、`eleven_v4` ≈ 780ms。既定は flash(`ELEVEN_MODEL_ID` で替える)。
2. **最初の 1 文を短く**: 指示文で「1 文は 40 字以内」。最初の文が短いほど、読み上げが早く始まる。
3. **thinking を切る**(最大の効き目)。**考えを短く**: 最初の `say` に載せる `intent` は 12 字以内。「見えた様子」は Claude に書かせず、画面側で作った言葉をそのまま出す(書かせると 1〜2 秒増えた)。
4. **先読み**: 文ごとに読み上げの取得を始め、前の文を話している間に次を用意している(`speaker.js` の `_pump`)。
5. **つなぎ**: 返事が来るまでの間は、うなずき(`NOD_AT_MS`)で間をつなぐ。数字は縮めない。縮めて見せるときは「一部を短くしています」と出す。
6. **聞き取りの遅れ**: ブラウザ内蔵の聞き取りは確定が遅いことがある。クラウドの聞き取りに替えたら、`t0ToSendMs` の差を測って書く。

## 測った記録と、学んだこと(2026-11-02、本物の Haiku `claude-haiku-5-5` と ElevenLabs flash)

**数字は 3 つに分けて書く。混ぜて「1.2 秒」と言わない。**

| 何の時間か | 測り方 | 結果 |
|---|---|---|
| ① あいづちの声が出るまで | 画面の `fillerMs`(`/api/metrics` の `filler`)。話し終わり(`t0`)から | 送信から 21ms(中央値、n=10、headless Chrome)。**本物の声では、声が止まったと判定するまでの約 0.45 秒が足される**(未測定) |
| ② 本当の返事の最初の音まで(サーバー内側) | `npm run measure -- 10`、間隔 5.5 秒 | thinking を切る前: 中央値 1795ms・90 番目 4244ms・1200ms 以内 3/10。切ったあと: 中央値 1345ms・90 番目 3920ms・4/10(n=10) |
| ③ 本当の返事の最初の音まで(画面の中、あいづちあり) | 画面の `totalMs`、送信から | 中央値 1158ms・90 番目 1826ms・1200ms 以内 6/10(n=10)。聞き取りの遅れは含まない |

- 遅れの正体は **API の最初の文字まで(TTFT)**。`node scripts/probe-haiku.mjs`(サーバーを通さず同じ指示文で直接呼ぶ)と比べると、サーバーの遅れではないと分かる。
- **効いたのは `thinking: {type:'disabled'}`**(交互に測って、中央値 1446 → 840ms、ばらつきも小さい。`effort: low` だけでは 1388ms で変わらず、thinking を切るだけで 836ms)。受付の短い返事には考える時間が要らない。`usage` の `thinking_tokens` は 0 のままなので、トークンの数からは分からず、時間で測るしかない。**設定を替えるときは、交互に測る**(API の揺れが時間帯で大きく、前後で比べると騙される)。
- 効かなかった: 指示文を短くする・出力の形を替える(`say` を先に、考えを 2 行目にする案 B は中央値 1851ms vs 1795ms)。キャッシュが効いていれば、指示文の長さは最初の文字までにほぼ効かない。
- **ヘッジ(最初の文字が 1 秒来なければ 2 本目を送って早い方を使う)は、効果を確認できなかったので、既定で外した**(`CLAUDE_HEDGE_MS=0`)。交互に 35 組(なし/あり)測って、最初の文までの中央値 922 vs 943ms、90 番目 1043 vs 1655ms。この 2 回は API が安定していて、2 本目が勝てるほど遅い回(約 1.9 秒超)が出ず、2 本目を送った 8 回はどれも救えなかった(送った回は 1.3〜1.7 秒で終わり、2 本目の最初の文字まで約 0.9 秒がかかるので、1 本目が 1.0〜1.7 秒の回は救えない)。使うなら、しきい値は 1800〜2000ms。遅い回が出る時間帯(最初の測定では 10 回中 2 回が 2 秒超)に測り直す。
- **プロンプトキャッシュは効いている**: 返事ごとの `usage` で、2 回目以降は `cache_read_input_tokens` が 1331〜1501、`cache_creation` は 0(`measure` の表の「キャッシュ読み」)。system は固定の文だけで、変わる物(見えている様子・言葉)は user のメッセージに置いている。キャッシュが外れる原因は、system の途中に時刻などを入れること・`thinking` や `output_config` を回ごとに替えること(最初の 1 回だけ書き直しになる)。
- 前の知識(`claude-haiku-5-5` を使う別の道具の測定、2026-11-01)では、最初の文字が約 0.6 秒だった。同じ設定(thinking を切る・最初の一文を短く)にすると、ここでも 0.8 秒前後まで縮んだので、**まず thinking を切る**。
- 1200ms を安定して切るには、まだ足りない。残りは、API の最初の文字のばらつき(0.7〜1.5 秒)・読み上げの最初の音(約 0.25 秒)・聞き取りの遅れ。あいづち(うなずきと短い声)で間はつなぐが、本当の返事の数字は縮まない。

## 会場の回線が悪いとき・声の無音(2026-11-02。外の資料の考え方を借りて試した)

- **回線の遅れを入れた測定**: `scripts/measure-network.mjs`(Chrome の CDP で、ブラウザ ⇔ サーバーの間だけに往復の遅れを入れる。スマホが会場の Wi-Fi 越しにつなぐ形)。テキストの回、3 回ずつ、中央値: 遅れなし 1131ms / 往復 +100ms 1056ms / 往復 +250ms・下り 1Mbps 1402ms(+270ms)。**+100ms は、API のばらつき(±150ms)に埋もれて見分けられなかった**。n=3 では、これ以上は言えない。パケット損失は CDP で作れず、未測定。
- **つまずき(数字が無効になりかけた)**: 指標の送信を止めようと `page.route`(通信の横取り)を使うと、**遅れが入らなくなり**、「+250ms でもほぼ同じ」という間違った結果が出た。止めたいときは、画面の中で `fetch` を包んで握りつぶす。さらに、条件ごとに小さな通信の往復を測り、遅れの 8 割に満たなければ「この数字は使えない」と出すようにした(スクリプトに入っている)。
- 遅れが効くのは、リクエストごとの最初の応答まで(ストリームの 2 つ目以降の塊には足されない)。課金の出ない仮の頭脳で調べると、`/api/chat` の POST は 4ms → 253ms、全部の読み切りは変わらず約 364ms。足し算の予想は「1 往復 × 2(会話と声)」だが、本物の頭脳では +250 のときに +270ms しか増えず、予想より小さかった。理由は未確認。
- **声の前後の無音は、削っても得がない**: 手元のあいづちの声(`eleven_flash_v2_5`)を `scripts/pcm-silence.mjs` で測ると、前の無音は平均 6ms、後ろは平均 25ms(ピークの -40dB 以下を無音とした)。最初の音までに余計な待ちは含まれていない。長い文で同じかは未測定(読み上げの枠を使うので、していない)。

## 守ること

- 目標を超えた回も隠さない。中央値と 90 番目の両方を書く。
- 仮の頭脳・字幕のみの回(`valid: false`)を、本物の数字として使わない。
- 読み上げの文字数は上限(`ELEVEN_DAILY_CHAR_CAP`)の枠を使う。測る回数は必要なだけにする。

## 声のモデルを比べる(2026-11-03、見本のキャラの VRM v4 と同じ 4 問で、flash と v4 Turbo)
- 手順: 同じ鍵・同じ声(Yui)で、`ELEVEN_MODEL_ID` だけ変えたサーバーを 2 本(8817=`eleven_flash_v2_5`、8818=`eleven_v4_turbo`)立て、`web/scripts/talk-through.mjs --port <ポート> --label <名>` を順に流す(Claude は毎分 12 回までなので並べて流さない)。1 回の通しは声を約 265 字使う。
- 結果: 最初の音まで 中央値 1,302 ms(flash、8 回)と 1,319 ms(v4 Turbo、4 回)、声の最初の 1 バイトまで 273 と 268 ms。**差は数十 ms の中に埋もれた**。Haiku が最初の文を出すまでが 0.8〜1.2 秒で、声のモデルより大きい。
- 見落としやすい差: v4 Turbo は声の音量の波が小さく、口の最大が 0.63(flash は 0.9 台)。口の開きは `speaker.level()` の「音量 × 6」で決まるので、声を替えたら口の最大(`aaMax`)も見る。
- 画面なしの Chrome は 8〜13 fps。口と声のずれは 1 コマ(77〜125 ms)より細かく言えない。端末の出力の遅れも入らない。実機の数字ではない、と書く。
