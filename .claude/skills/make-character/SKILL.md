# make-character: 言葉か絵から、話すゆるキャラまで(7 段の入口)

細かい手順は各段のスキルにある。ここは、いちばん先に読む「道具の場所と止まらない決まり」、7 段の順番と段の間で渡す物、確かめの命令だけ。


## 確認が出る時(先に 1 行だけ言う)

確認(許可の画面)は、話すことや覚えたことが変わる時・PC の外を読む時・お金や長い時間を使う時・戻しにくい時・外へ出す時だけ出る。読む・下書き・点検・変わる所の表示・一覧・自分の試験では出ない(`.claude/settings.json` の決まり。全体は `docs/confirmations.md`)。
確認が出る道具の直前に、次の 1 行だけを言う。会話で別に「いい?」とは聞かない(同じことを 2 回聞かない)。

| する事 | 直前に言う 1 行 |
|---|---|
| 消す(`rm`) | 「<名前>を消します。ゴミ箱に入らず、戻せません。次に出る画面が、その確認です。」 |
| 外へ出す(`git push`・`gh`・`vercel`) | 「<どこ>へ出します。はい → ほかの人にも見えます。戻す → 取り下げ(すぐには消えません)。次に出る画面が、その確認です。」 |
| 話し方の文を手で直す(`persona.md`・`character.json`) | 「<名前>の話し方を書き換えます。先に前の版を creator/work に取っておきます。次に出る画面が、その確認です。」 |
| 守りの部品を変える(`.claude`・`tools`・`creator/learn`・`creator/pipeline`・`creator/review`・`creator/setup`・`web/src/conversation`) | 「この子を守る仕組みを変えます。ふつうは要りません。頼んだ覚えが無ければ『いいえ』を押してください。次に出る画面が、その確認です。」 |
| 作る画面を起こす | 「作る画面を起こします。同じ Wi-Fi のスマホからも開けます(合言葉つき)。止める → 窓を閉じる。次に出る画面が、その確認です。」 |
| 3D にする(`run_built.sh`・`run_groups.sh`) | 「3D にします。約 20 分、Claude の使える量をたくさん使います。途中で止められ、作りかけは creator/work に残るだけです。次に出る画面が、その確認です。」 |
| 鍵 | 聞かずに止める: 「鍵はここに貼らないでください。画面の鍵の欄に入れてください。」 |

- 初めて作る人には、最初に 1 回だけ「頼んでいない確認が出たら『いいえ』を押してください」と言う。
- 確認で「いいえ」を選ばれたら、別の道具や書き方で同じことをしない。止まって、どうするかを聞く。

## 先に読む: 道具の場所と、止まらない決まり
- **道具はリポジトリの `creator/` にある**(`builders`・`pipeline`・`review`・`draw`・`check`・`setup`)。作業フォルダが リポジトリの中でない時は、リポジトリから `git worktree add <作業用の場所> <枝>` で取り出し、その中の `creator/env.sh` を読み込む(`ENV_SH=<作業用の場所>/creator/env.sh; . "$ENV_SH"` で REPO・BLENDER・PY・TRIAL_BASE が決まる)。手元の値は `python creator/setup/doctor.py --write` が調べて `creator/env.local.sh` に書く(リポジトリには入れない)。
- **道具が無い・場所が分からない時は、聞き返さない。** `hand-built-character` の手組み(Blender だけ)で進め、省いた確かめ(`check_all.sh`・`pk02`・`j01`・会話の画面での確かめなど)を、最後の報告に「省いた確かめ」として書く。質問だけで終わると、3D も写真も 0 枚になる(11-08 の一発の試しは、場所を聞き返して 37 秒で止まった。スキル本文の `creator/` の言及は 76 か所あったのに、場所はどこにも書いていなかった)。
- **絵だけ渡された一発の道**(「話せる 3D にして」と 1 行だけ頼まれた時。三面図でも同じ):

| 順 | すること | 残すもの |
|---|---|---|
| 1 | 絵を読む。三面図なら 正面・横・後ろ の 3 枚と気づき、守る目印(体と手足の色・胸や背中の模様・小物・しっぽの形など)を 5〜6 個書き出す | `settings.md` の目印の表 |
| 2 | Blender で手組みする(`hand-built-character`。部品ごとに、色と目印を元の絵のとおりに) | `creator/builders/<id>.py`、`model.glb` |
| 3 | **正面・斜め・横・後ろの 4 枚を撮り**、元の絵と見比べる。目印の抜け・凹み・穴・数の違いを探す | 4 枚の写真 |
| 4 | 合格なら取り付ける(下の ⑦ の `t07_talk.py`)。だめなら直すのは 1 回だけで、直した差を書く | `characters/<id>/` |

  **4 枚の写真は、必ず出力フォルダ(`pictures/`)に置く。** 写真が 0 枚のまま終わらない(判定する人が見る物が無くなる)。止まった所・省いた確かめも報告に入れる。

## 人の確認(契約 K3)と段の道具(2026-11-06 夜から)
- キャラに確認の状態(`creator/work/<id>/review/state.json`。`python creator/review/review_state.py init <id>` で作る)があると、段の道具が自分で止まる。
  - `stage_run.py`(claude・tool)と `t07_talk.py` は、段 N の前に `review_state.py can-start <id> <N>` を呼び、前の段が `ok`(人が OK)か `auto`(門の無い段が済んだ)でなければ、流さずに終わりの番号 2(run.jsonl にも書かない)。やり直し中(`redo`)も止まる。
  - `--upto M` で段 N〜M をまとめて頼むとき、途中で終わる門(C0=段 0・C2=段 2・C3=段 3〜4・C5=段 7)があれば止まる(門を人の確認なしに越えない)。C3 は段 3・4 をまとめて見る門なので `--stage 3 --upto 4` で作る(段 3 だけは断る)。最後の段が門なら、済んだあと `--publish-right <絵>`(C0 は描いた SVG、C2 は正面の絵。`--publish-views`・`--publish-sheet` も)でスマホに出す。
  - 済んだ段は `stage <id> <N> done`(門の無い段は `<N>.json` が auto で書かれる)。落ちた段は `failed`。部品は `creator/pipeline/review_gate.py`(K3 の CLI だけを呼ぶ)。
  - `--review auto`(既定: 状態があるときだけ見る)・`on`(状態が無ければ止める)・`off`(見ない。記録の `review` に off と残す)。夜の無人の試しは状態を作らずに流す(`review: none`)。
- 試験: `python -m unittest creator/skilltest/test_review_gate.py`(12 件。本当に stage_run を流す。人の判断は確認画面のサーバーと同じ `make_request` で作る)。壊した版 4 つ(素通り・範囲の門を見ない・門の途中で終わる範囲を許す・done にしない)で落ちることを確かめた。
- C3・C5 の画面はまだ無い(11-06)。確認の状態を作ったキャラは、段 3〜4 が済むと C3 の人の OK まで段 5 へ進めない(それが正しい止まり方)。
- `t07_talk.py` で作り直しを取り付けるとき、同じ言葉(`--words`)なら `origin`(生まれた時の記録)を変えない(前は `created` が今の時刻に書き換わった)。

## 作例の判定のやり直し(2026-11-06 夜。結果の表は `creator/skilltest/結果表.md` の末尾)
- 撮り方: `creator/viewer/serve.py <空いた番号> --mount=/trial=<リポジトリ>/characters` を自分で起こし、`node creator/skilltest/shot_browser.mjs <番号> /trial/<id>/character.json <出力>/<id>/browser` を体ごとに流す。5 体を機械の札 1 本(`--minutes 10`)の中で撮って 13 秒。判定役(claude -p)は札の外で流す。404 は favicon だけで、絵には関係ない。
- 判定は `j01_judge.py` の `prepare` と `judge_many` を 5 体まとめて呼ぶと、Haiku は並べて Sonnet は 1 つずつ流れ、5 体で 146 秒・定価に直した目安 0.30 ドル。
- **「色」で落ちたら、まず D の行を読む。** 作例では、元の色そのものより、光(画面の目の発光・中から光るグラデーション)・つや・縁(ベゼル)の差を、判定役が「色」と答えていた。直すなら発光・つや・縁から。
- **比べの絵の並べ方(元の絵の余白)は、合否を変えなかった。** 元の絵の余白を切ってブラウザの正面と同じ割合で写しても、5 体の合否は全部同じで、動いたのは Haiku の数が 1 つずつだけ。みかんの「口が大きい」は余白を切っても残った。大きさの言い分は、目の間を物差しにした数字で確かめる(上の r2 の記録)。
- 同じ撮った絵を 2 回流すと、Haiku の数は 0〜1 動くことがある(robo の色 1→0 など)。合否の境目(2/3)にいる軸は、2 回流して両方を書く。

## 動画の素材: 回る動画と、段 ⓪〜③ の育つ帯(2026-11-06 夜)
- 命令: `creator/viewer/serve.py <空いた番号> --mount=/trial=<リポジトリ>/characters` を自分で起こし、体ごとに `node creator/skilltest/turntable.mjs <番号> /trial/<id>/character.json <出力>/<id> --stills`(既定 6 秒・1920x1080・30fps・背景 #f2f2f2・音なし・メタデータなし)。そのあと `python creator/skilltest/grow_strip.py <id> --stills <出力>/<id> --out <帯.png> --plain <字なし.png>`。作例 5 体を機械の札 1 本(`--kind gpu --minutes 8 --wait 60`)で 35 秒(主役の札が先にあり、4 分待ってから流れた)。サーバーは自分の PID だけ止める。404 は favicon だけ。
- **時間を止めて撮る**: 読み込みの後で `requestAnimationFrame` と `performance.now` を差し替え、1 コマずつ 1/30 秒進めて、`canvas.toDataURL`(確かめ画面は preserveDrawingBuffer)を ffmpeg の image2pipe へ流す。撮る速さに関係なく、待つ間の動きとまばたきが動画の時間どおりに進む。差し替えた後の `waitForFunction` は `polling: 100`(rAF で待つと止まる)。
- **カメラの距離**: 外接の円柱に半径の余白を足す決め方では、キャラが画面の 6〜7 割に小さくなった。頂点を 3 万点まで間引き、36 の向きに回して全部が画面の 8 割に入る最小の距離を二分探しで決めると、切れずに大きく写る。
- **形だけの絵(②)**: ページに THREE が無いので、今の MeshStandardMaterial を clone して、色・絵・発光・頂点の色を外す。毛の殻(`<名>_fur<n>`)と表の顔の面(`c.face.mesh`)は隠す。骨と表情のキーはそのまま動く。
- **① の重ね(builder の D)**: 実行せずに ast で読み、絵の上に 7 割以上のる形だけ描く。ただし「のる」の判定は、体の上に落ちた読み違いを見つけられない(ちょうちんくんの `flap_path` の x は真ん中からの距離で、初めは胴の上に丸が並んだ)。新しい読み方を足すときは、builder の中の使い方を先に読む。パネルくんの D は、腕の x は絵の座標、脚と足の x は真ん中からの距離(同じ D の中でまざる)。口の `_a/_b/_c` は b を制御点にした 2 次のベジェ。
- **正直に書く**: ② は出来上がりから色を外した物で、段 ② の時の途中の物ではない。① の数字は builder の今の値(直した後)。素材と一緒に一覧(ファイル・中身・作り方・時刻・commit)を置く。素材と一覧は、動画の流れの素材のフォルダ(リポジトリの外)に置き、リポジトリには入れない。
- 試験: `python -m unittest creator/skilltest/test_grow_strip.py`(6 件、1.3 秒、GPU なし)。`python -I` を付けると `creator/...` の形の名前が読めないので付けない。

## 作例の検査(契約 K0)と改行(2026-11-07)
- 命令は `python creator/setup/check_samples.py`(1 秒・GPU なし。くわしくは `creator/setup/README.md`)。作例をわざと作り直した時だけ `--write-hash` で基準を書き直し、コミットの文に理由を書く。
- ④ の sha256 は、文字のファイル(`.gitattributes` の `text eol=lf` と同じ種類)の CRLF を LF にそろえてから取る。作例に新しい種類の文字のファイルを足す時は、`.gitattributes` と `check_samples.py` の `TEXT` の両方に足す。11-07 まで `.svg` をそろえておらず、基準が Windows の CRLF の形だったので、LF で取り出した木(Mac・Linux と、`.gitattributes` の後の新しい写し)で `body.svg` が落ちていた。
- **改行に左右されない事は、リポジトリの外の写しで確かめる**: `git -c core.autocrlf=false -c core.eol=lf worktree add --detach <写し> <コミット>` → `git ls-files --eol | grep -c w/crlf` が 0 → 検査が合格 → 直す前の 2 本に戻すと落ちる(対照。11-07 は ④ が body.svg で不合格 1)→ `unix2dos` で 1 本を CRLF にしても合格。片付けは `git worktree remove <写し>`(消さずに残す時は、写しを動かしてから `git worktree prune`)。
- Windows の Git は `core.autocrlf=false` だけだと、`text=auto` のファイルを CRLF で出す(既定の `core.eol` が CRLF)。`core.eol=lf` も付ける。設定ごとの出方は、取り出さずに `git -c <設定> cat-file --filters --path=<名前> <blob>` で測れる(git 2.51 で測った)。
- `core.autocrlf=true` で取り出した木に `.gitattributes` を取り込んでも、触っていないファイルは CRLF のまま、合わせで書きかわったファイルだけ LF になる(1 つの木に混ざる)。`git apply` は CRLF の作業ファイルにも LF の patch を当てられ、当てたファイルは `eol=lf` の形(LF)で書かれた。
- **ほかの流れが作例のファイルを変える時は、基準の直しと「対」で入れる**(第 7 波、11-07。人格の文 `persona.md` は会話の流れの持ち物だが、④ の基準に入っている)。相手が基準の行だけの控え(patch)を作り、こちらが `git apply --check` → `git apply` → 1 本でコミットする。どちらか 1 本だけでは ④ が落ちるので、合わせは 2 本を続けて入れ、門は 2 本の後に 1 回。
  - 当てる前に、新しい値を相手のコミットの中身から自分で計算して比べる: `git show <相手>:<パス> | tr -d '\r' | sha256sum`。古い値が今の基準と同じか、相手と今の木で違う作例のファイルが控えの本数と同じか(`git diff --stat HEAD <相手> -- characters/<id>`)も見る。
  - 写しの木での確かめ: LF で取り出す(上の行)→ `git merge --no-ff --no-commit <相手>`(コミットを作らない)→ 合格 → 作例の文字のファイルを全部 CRLF にしても合格。対照 2 つ: 自分の 1 本だけ → ④ NG(変わった本数が相手の分と同じ)/ 相手を入れたまま基準だけ前の版に戻す → ④ NG。2 本の合わせのぶつかりは `git merge-tree --write-tree <自分> <相手>` で書かずに見られる。
  - 対は id ではなく中身で決まる。相手が線を付け直して id が変わっても、ファイルの blob の番号(`git rev-parse <コミット>:<パス>`)が同じなら基準はそのまま使える。中身が変わったら控えを作り直してもらう。

## 変換の絵から組む(作る道から 3D を頼まれた時。第 12 波 b)
作る道(初めての会話)で使う人が「3D にもする?」→ 形と しつかんを選ぶ → 変換の絵を OK すると、`creator/review/yuru_make.py` が受け渡しの紙 `creator/work/<id>/convert/handoff.json`(schema `yc-convert-handoff/1`)を書く。3D は**この紙から**始める(本人の決め: 絵から全く同じ物を作るのは難しい。3D はゆるキャラに変換されて出てくる物でいい)。変換の絵の描き方は yc-0-draw の「3D 用のゆるキャラ変換」。

| 欄 | 中身 | 使い方 |
|---|---|---|
| `picture.svg`・`picture.png` | 変換の絵(使う人が「この かたちで 3D に する」を押した絵) | **3D の形の元はこれ**。部品の `<g id>`(K1)が部品の表になる |
| `original.svg` | 最初に「この子にする」を押した絵 | 色と目じるしの確かめだけ(形は追わない) |
| `shape` | `atama`(あたまでっかち)/ `maru`(まるい胴) | 体の型。頭の高さ = 全身の 0.5(atama)、胴 1 つ(maru) |
| `material` | `fabric` / `fur` / `vinyl` | `looks.3d.material` にもう書いてある(画面の しつかんの既定) |
| `role` | home・shop・station・facility | 人格の文の「- 役目:」。3D では変えない |
| `settings` | 変換の絵の settings.md | 残した目じるしと、変えた所。3D でも同じ目じるしを残す |

- **元の絵とまったく同じにしない**(画面でも「もとの えと まったく おなじには ならないよ」と言ってある)。形は変換の絵、色は元の絵の色。目じるし(耳の形・お面・しっぽの長さ・色・持ち物)は settings.md の表のとおりに残し、小物を足さない。
- しつかん: ぬの → いつもの材質(フリースの型: 粗さ 0.86 + 布の照り)。け → いつもの材質に毛の殻(`creator/viewer/furShell.js`。重いので三角形 3.6 万以下)。つるつる → つやのある材質(粗さ 0.55 + クリアコートの上塗り + 面の照り 0.6)。GLB は材質を差しかえて画面で替えられるので、**材質ごとに GLB を作り分けない**(render-device の「しつかん」)。
- できたら character.json に `model` を足す。`looks.default` は `3d` にしてよい(2D は `looks.2d` に残っているので、画面の切り替えで戻せる)。`looks.3d.material` は消さない。2D(`characters/<id>/2d`)は消さない・作り直さない(使う人が 3D を待つ間に話していた子)。
- 確かめ: 部品の表の名前と数が、変換の絵の `<g id>` と同じか。目じるしが 3D の 5 方向の写真に全部あるか。画面で 3D と 2D を切り替えて、別の子に見えないか(色と目じるし)。

- できないことを、できると言わない。測った数字と、確かめていない事を分けて書く。

5. 口元は、元の絵と同じ割合で並べて拡大する(ピンクの楕円の幅の 1.6 倍の四角)。口の幅 ÷ ピンクの幅 は 0.80 と 0.78 で同じでも、前歯が 2 つの四角で浮く・鼻の上が直線の Y、で表情が変わった。数字だけで OK にしない。
6. 2D は正面の差(平均 1.1/255、形の重なり 0.990)が小さくても、動きの静止画(手を振る・おじぎ・首かしげ・表情の一覧)を 1 枚ずつ見る。板を回すと肩に細い線、おじぎで頭が蝶ネクタイを隠す、考え中のまま話すと口が笑顔に替わる、が出た。

### 判定の一覧の絵(スマホの 400 px 幅で読める)
- 幅 1800、文字 58〜78 px(幅の 3.2% 以上)、BIZ UDPゴシック 太字(BIZ-UDGothicB.ttc の 1 番)。上の段 5 列: 元の絵 | 2D | 3D 正面 | 3D 横 | 3D 後ろ と、その下に ○△ の一言。下の段: 元の顔 | 2D の動き | 3D の顔 | 元の横 | 元の後ろ。問題の所は赤い輪+番号。番号は顔に重ねず、外へ線で出す。最後に「直す順」。
- 図の範囲は、地の色との差 > 12 で取って穴を埋め、4% の余白で切り、セルへ縦横比のまま入れる。地の色: 元の絵の白抜き 255・2D の静止画 204・3D の 8 方向 244。手袋の白は元の絵の地と同じ 255 なので、穴埋めで図に入れる。

## 3D と元の絵を比べて測る・判定役に見せる時の学び(第 5 波、2026-11-07)

### 測る場所は 3D の点から決める
- builder が作業フォルダへ `samples_at.json`(あご・おなか・しっぽ・鼻先・前歯・目の 3D の点)を書き、8 方向の撮影の中で **gltf.scene の世界の行列 → カメラ**で画素に直す。目で選んだ座標より取り違えが無い。
- 輪郭の黒い線にかかる点は、色ではなく線との混ざり(差 99 などの外れ値)になる。周り 9×9 に黒(最大の明るさ 70 未満)があれば数えない。5×5 の中央値で測る。
- 「白」を数える時は背景(242)を数えない(白は 246 より上)。数え方を直す前は、前歯の白が 400 画素もあるように見えた(背景)。

### 撮り方で見え方が変わる
- **待機の動き(idle)が流れたまま撮ると、撮る瞬間ごとに頭の向きが揺れ、90 度の目が輪郭にかかったりかからなかったりした**。比べる写真は `mixer.setTime(0)`・`timeScale = 0` で止めてから撮る(`--freeze`)。
- 横の写真は遠近で、目から鼻先までが 8% 短く写る(写真 79 px・正射影 149 px の位置 = 絵 86 px と同じ)。元の絵(正射影)と比べる横顔は、**同じ描き方で 12 m から同じ広さが入る狭い画角で撮る(望遠、`--tele`)**。
- 横の切り抜きの倍率は、横の写真の中の目と前歯の上下の間隔で決める。正面の目の間隔から決めた倍率(0.724)は、顔がカメラに近い分だけ大きく、横では 7% 小さく切れた(横の倍率 0.678)。

### 判定役(Claude の Haiku 5.5・Sonnet 5.5、各 3 回)
- 同じ前の 3 枚の絵でも、Haiku の「色」は 1/3・2/3・3/3 と回ごとに揺れた(Sonnet は 3/3 のまま)。数字の測り(クリームの差)と組にして書く。
- 横顔の問いは 2 つに分ける: 「目・鼻先・前歯が見えるか」(判定のもとの指摘)と「形・大きさ・位置が近いか」(厳しい)。理由の行(D:)は 6 回とも「前歯が横から小さな点」で一致した。
- 判定の絵に横の全身を並べると 3D が小さく写るので、横顔は元の絵と同じ倍率のアップを並べる。
- 判定は 1 回 50 秒ほど、72 回で定価の目安 0.67 ドル(定額のプラン。`CLAUDE_CODE_*` と鍵を外した `claude -p`)。


## 3D の横顔を判定役に見せる時の学び(第 6 波、2026-11-07)

### 撮影の 404 の正体
- 8 方向の撮影のたびに出ていた「404」は **`GET /favicon.ico`**(Chrome がページの絵を自動で取りに行く。確かめ用のページに絵の指定が無く、Python の簡単なサーバーが「File not found」を返す)。
- Playwright の response の記録には出ない(ページの外の取りに行き)。**サーバーの記録を捨てずにファイルへ残すと、パスが分かる**(shot8_w6.sh の server.log)。
- ときどき出る「failed: …/motions/idle.glb」は 404 ではなく、撮り終わってブラウザを閉じた時に取り消された読み込み。
- 止めたいなら、確かめ用のページに `<link rel="icon" href="data:,">` を足す(画面の流れの持ち物)。害は無い。

### 判定役の見方と、数えた大きさ
- 判定役(Claude の Haiku 5.5・Sonnet 5.5、各 3 回)は、横の全身の絵と横顔のアップの両方を見て「前歯が小さい」と答え続けた。
- **同じ判定の絵の中で前歯の白い画素を数えると、3D は元の絵と同じかそれ以上**(全身 28 対 31 画素、横顔のアップ 505 対 371 画素。直す前は 14・94)。数えた値を判定の結果と並べて書く。
- 見えやすさを上げたもの: 前歯を輪郭の線の内側へ入れる(背景の上に白を置かない)、前歯の黒い縁を太く(1 → 2.5 mm)、前歯を光によらない白に、顔の望遠で細かく撮る。最後の判定は 横顔が見える 1/3・2/3、近い 0/3・2/3(Sonnet は合格)。
- 理由の行で残った指摘: 横から見た目が元より小さく細い、ピンクの鼻先が縦に細い。前歯の次に直すならこの 2 つ。
- 判定は 108 回・定価の目安 1.08 ドル(定額のプラン)。1 回の判定(正面と横、12 回)は約 55 秒。
